How you use it

  1. Open a workspace from any GitHub repo. The chat and the live preview come up side by side.
  2. Turn on Annotate.
  3. Hover over the preview to see each element outlined with its name.
  4. Click an element and add a note. A numbered badge marks the order.
  5. Press Send and watch the preview reload as the agent edits.
  6. Badges turn green when the agent has changed what you pointed at.

How agents use it

Each selection reaches the agent as structured context plus pixels:

  • CSS selector to find the element in the source
  • Text snippet to tell apart elements that share a selector
  • Bounds in page coordinates
  • A screenshot crop of each element, plus a viewport shot with the numbered badges
  • Click order, when the order matters
  • Your note, word for word

Agents talk back

  • Steer mid-turn: a message sent while the agent works joins the running turn
  • Ask before it runs: every shell command waits for your approval
  • Show the cost: tokens and a list-price estimate per call, or no number when the price is unknown
  • Report edits: touched files stream back as diffs while the preview reloads

Best practices

  • Be specific: “CTA text is unclear” is better than “fix this”
  • One change per selection: the agent can address and confirm each one
  • Use ordered mode for flows: click 1 → 2 → 3 to describe a sequence
  • Annotate the state you're in: open the menu or dialog first, then point at it
  • Pause animations to point at a single frame

Annotation

The fastest way to tell an agent what to change is to point at it. Every step below has its own visible state, on desktop and on touch.

The flow

  1. Turn on Annotate from the preview toolbar. The preview gets a soft outline so you know clicks won't reach your app.
  2. Hover to see the element's name above it, like a.cta. On touch, tap instead.
  3. Click to mark it. A badge shows its number in ordered mode, or a dot in unordered mode.
  4. Add a note in the card that opens next to the element. Each element keeps its own note.
  5. Send. Marked elements ride along as chips; the agent gets their names, text, position and a screenshot.
  6. Resolved. When the agent's edit changes a marked element, its badge turns green.

Install

Run the whole platform on one machine with Docker Compose. You need a GitHub OAuth app and about five minutes.

Prerequisites

  • Docker with Compose v2
  • A GitHub account to register an OAuth app
  • Optional: a HashiCorp Vault for per-project secrets

1. Create a GitHub OAuth app

Go to GitHub developer settings and choose New OAuth App.

FieldValue
Application nameShram
Homepage URLhttp://localhost:3000
Callback URLhttp://localhost:8083/auth/github/callback

The callback must match exactly. It is the auth service's OAuth endpoint.

2. Create .env

./scripts/setup.sh   # writes .env and checks Docker

# then fill in the two required values
GITHUB_CLIENT_ID=…
GITHUB_CLIENT_SECRET=…

3. Start it

./scripts/dev.sh     # Postgres, auth :8083, workspace manager :8081, proxy :8082, web :3000

Open localhost:3000, sign in with GitHub, pick a repo and choose Create workspace.

Per-project config

Add .shram.yaml to a repo to control secrets, env and the dev command. Shram reads it through the GitHub API before the container starts. No file means defaults, not an error.

name: my-app
secrets:
  vault_path: "secret/data/projects/my-app/dev"
env:
  NODE_ENV: development
services:                     # proxied via /__svc/{name}/
  auth: https://auth.staging.example.com
dev_command: "pnpm dev"

Features

What a workspace gives you, from the container up to the chat pane.

Workspaces

Each workspace is an Ubuntu 22.04 container with code-server on 8080, your dev server on 3000 and the agent daemon on 4100. Node 20, pnpm 9 and Git credentials are ready, and secrets are written to .env.local. Restart runs the same provisioning path as create, so secrets, ports and routes always come back.

Live preview with HMR

The preview is served through the proxy at /ws/{id}/preview/. WebSocket upgrades are relayed in both directions, so Vite and Next.js hot reload work inside the iframe without exposing raw ports.

Annotation modes

ModeBadgeUse it for
Ordered1, 2, 3Flows and sequences. Click order is sent to the agent.
UnordereddotIndependent fixes. Order is ignored.

A selected element keeps an edit counter. When the agent's change re-renders it, the badge updates, so you can see what was touched.

Screenshots

Each element is captured the moment you confirm it, from the page as it is right now: open menus, typed input and scroll state included. If a capture fails, the message still goes out with the structured context. A failed screenshot never blocks a send. How the capture engine works.

Steering and stop

Send while the agent works and your message joins the running turn at the next step boundary. A running tool batch finishes first. A model call in flight is cut and asked again with your message. Stop is the only hard abort.

Tool guardrails

  • Every file path goes through a realpath and prefix jail. Absolute paths, .. and symlink escapes are rejected.
  • Search runs grep from an argument array, never a shell string.
  • run_command runs only after you approve it.

Cost estimate

Every model call reports input, output and cache tokens. Prices come from a catalog that the control plane fetches and pushes to the workspace. A model without a known price shows no cost rather than a guess.

Secrets

Point .shram.yaml at a Vault KV path and the values are injected at provision time. They never pass through the browser.

Images

  • One crop per element, captured when you confirmed it
  • One viewport composite at send time, with the numbered badges in the picture
  • A staleness check: selections whose element has since left the page are listed by selector

Images reach the model as native image blocks. For text-only backends they are replaced by a short marker, so the model knows a picture existed.

Capture metrics

Every capture reports its own timing, cache hit rate, longest main-thread chunk and which encoder ran. Slow pages show up in the data, not in user complaints.

Proxy

One Go reverse proxy carries every IDE, preview and agent byte. The browser never sees a container port.

Routes

PathTarget
/ws/{id}/ide/*container :8080 (code-server)
/ws/{id}/preview/*container :3000 (your dev server)
/ws/{id}/agent/*container :4100 (agentd)
/__svc/{name}/*services from .shram.yaml
/internal/routesroute registration, internal token only

Auth

/ws/* and /__svc/* need a JWT as a Bearer header or the shram_token cookie. The cookie is how iframes authenticate, since they can't set headers.

The one rewrite

Preview HTML is the only response the proxy changes. It adds one script tag before </body> and fixes Content-Length. Every other response passes through byte for byte. DISABLE_PREVIEW_OVERLAY=1 turns the rewrite off.

kshan क्षण

“An instant.” The capture engine behind annotation screenshots, built as its own package because the first version couldn't capture busy pages at all.

The problem

The first serializer copied every computed style of every node, in one blocking pass, inside the user's app, often in a background iframe on a shared cloud CPU.

NodesOld walkSVG sizeResult
4211,447 ms4.3 MBPage frozen for 1.5 s
2,8019,314 ms28.8 MBPast the 5 s timeout, capture fails

The fix

  • Memoized style reads: work scales with unique components, not nodes
  • Time-sliced walk: 8 ms main-thread chunks, so the page never janks
  • Encoding in a worker: JPEG work leaves the main thread, with a fallback under strict CSP
  • Built-in metrics: every capture reports its own timings

The rule: move everything movable off the main thread, and make whatever has to stay interruptible.

Agent

One agent core, two front ends: the web chat pane and a VS Code extension.

Shape

  • packages/agent-core: the loop, jailed tools, providers and the protocol. It has no vscode dependency.
  • apps/agentd: a WebSocket daemon on :4100 that the chat pane reaches through the proxy
  • extensions/shram-agent: a thin VS Code webview over the same core

Providers

Cloud models through any compatible API and local models on the workspace all run through the same steering harness, so mid-turn messages behave the same on every model.

FAQ

Do I need to install anything?

No. Shram runs in the browser. Sign in with GitHub, pick a repo and the workspace starts in the cloud.

Does annotating change my app?

No. Annotate mode catches your clicks so they don't reach your app, and turning it off gives the preview back unchanged.

Can I use it on an iPad or a phone?

Yes. iPad keeps chat and preview side by side, and phones put the chat first with the preview one tap away. Annotating works by tapping.

Does the agent run commands on its own?

No. Every command waits for you to tap Allow.

What if a screenshot of my selection fails?

Your message still goes out with the element's name, text and position. Sending is never blocked.

Why not take screenshots in a headless browser?

It loads a fresh page, so any state you reached by clicking around is lost. It would also add 150–300 MB to every workspace and slow down startup.

Does the overlay touch my HTML?

The proxy adds one script tag to preview HTML. It does nothing until the chat pane sends a handshake. DISABLE_PREVIEW_OVERLAY=1 turns it off.
